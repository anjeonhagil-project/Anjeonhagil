2 실행과 DB 적재 — 처음부터 따라가는 순서

2.1 준비와 검사

A*·ML의 로컬 계산에는 Python 3.12가 필요하다. 서비스 앱 실행에만 Node.js·npm·기존 Supabase 프로젝트가 추가로 필요하다. 이 환경의 검증 버전은 Python 3.12.14, Node 24.19.0이다. 아래 명령은 data·tools·database가 바로 보이는 폴더에서 실행한다. 데이터셋 ZIP은 Anjeonhagil_DATASET_FINAL, 전체 ZIP은 Anjeonhagil_FINAL/dataset 폴더다. Windows에서는 python이 Python 3.12인지 확인하고 가상환경의 Scripts/python을 사용한다. macOS/Linux는 .venv/bin/python을 사용한다.

python -m venv .venv
.venv/bin/python -m pip install -r tools/requirements-service.txt
.venv/bin/python tools/check_release.py
.venv/bin/python tools/calculate.py

check_release는 전달 형식을 자동 판별하여 파일 해시, 보존된 옛 정적 계약, 현재 보호구역 전수 공간 검산, 현재 시간대·A*·학습 계약을 실제로 다시 실행한다. 저장된 성공 보고서만 읽고 통과시키지 않는다. 해시만 빠르게 검사하려면 --hash-only를 붙인다. calculate는 동봉 OD10의 고정 출발시각으로 새 시간·raw6·coverage를 출력한다. 시간대 검사만 하려면 tools/validate_hourly.py를 실행한다. 실행 결과는 기본적으로 현재 작업 폴더의 *.local.json이며 동봉 evidence는 덮어쓰지 않는다. 검증 결과는 evidence/hourly_validation.json에 이미 포함했다.

2.2 DB 스키마 생성과 적재

첨부 서비스는 Supabase의 인증 사용자·회원 테이블을 쓰고 있었다. 스키마 원문은 database의 두 SQL이며 전체 ZIP의 service/database/final과 내용이 같다. 신규 테이블은 ag_ 접두사로 추가하며 기존 road_nodes·road_links·users·기존 선호 테이블을 덮어쓰지 않는다. OSM arc ID를 기존 표준링크 ID 자리에 넣지 않는다.

기존 운영 DB가 있다면 baseline SQL을 재실행하지 않는다. 빈 개발 프로젝트를 시작할 때만 service/database/baseline의 00~07을 기존 서비스 설치 순서대로 적용한다. 그 후 다음 절차를 따른다. 실제 DB 연결 문자열은 로컬 환경변수 DATABASE_URL로 설정한다. README나 Git에 비밀번호를 적지 않는다.

.venv/bin/python tools/manage_database.py migrate
.venv/bin/python tools/load_database.py --dry-run --report /new/path/load-check.json
.venv/bin/python tools/load_database.py --load
.venv/bin/python tools/manage_database.py status
.venv/bin/python tools/load_database.py --load --activate

migrate는 기존 users.id가 UUID이고 onboarding이 boolean인지 확인하며 새 ag_ 구조가 이미 있으면 중단한다. 두 SQL은 하나의 트랜잭션에서 적용한다. 적재기는 8개 데이터 테이블을 COPY로 넣고 건수를 대조한 뒤 ready로 바꾼다. 같은 release에 다른 manifest를 덮어쓰지 않는다. 이미 동일한 ready 버전이 있으면 건수를 확인하고 재사용한다. 활성화는 마지막 별도 단계다.

전체 내보내기는 약 331만 행이며 JSON 원속성·인덱스가 추가되므로 압축 ZIP 용량만으로 DB 저장공간을 판단하지 않는다. DB 용량과 서버 메모리를 먼저 확인한다. A* worker는 그래프를 메모리에 올리므로 정적 호스팅이나 짧은 실행시간의 함수 대신 계속 실행되는 Python 프로세스가 필요하다. 이번 검증 환경에서 그래프 로딩 후 worker의 대기 메모리(RSS)는 약 1.59GiB였다. 512MB 메모리 환경에는 그대로 배포할 수 없다. 로컬 PC 또는 여유 메모리가 있는 실행 서버에서 먼저 인수한다. 워커 1개는 요청을 순서대로 처리한다. 다중 사용자 부하는 별도 운영 용량 검토 대상이다.

로컬 계산·검증·A* 탐색·ML X8 생성에는 서비스 앱·API 키·원격 DB가 필요 없다. tools/calculate.py는 tools/examples/hourly_request.json을 읽고 현재 raw6·시간·coverage를 반환한다. Python에서 tools/api.py의 TeamCalculator와 learning 함수를 사용하거나 tools/serve.py의 /search·/evaluate를 호출한다. /evaluate에는 예제처럼 5개 버전과 출발시각을 함께 보낸다.

2.4 서비스 소스가 필요한 작업

이 데이터셋 ZIP에는 React·Express 앱, users 초기 스키마, 서비스 테스트용 Node 패키지가 없다. 본문에서 service/로 시작하는 경로는 전체 서비스 ZIP의 위치를 설명하는 참고다. tools/test_service_connection.py는 전체 ZIP 전용 선택 검사이며 데이터셋 완료 조건이 아니다. 기존 서비스 연결은 전체 FINAL_CHILD100 ZIP을 사용하는 DB·백엔드 담당이 맡는다.

A*·ML 담당은 Python 설치 → tools/check_release.py → tools/calculate.py가 통과하면 현 데이터로 작업을 시작할 수 있다. 학습은 실제 노출·선택을 모은 뒤 수행하며 제공된 시험 선택을 실제 Y로 쓰지 않는다.

3.3 주중·주말·시간 경계

KST(Asia/Seoul), 월~금 주중·토/일 주말, 0~23시다. 공휴일은 따로 분리하지 않는다. 원문 ~01은 00:00~01:00, ~24는 23:00~24:00으로 읽는 프로젝트 채택 해석을 metadata에 고정했다. 공식 원문에 시작·종료 경계의 추가 인증이 있었다고 표현하지 않는다.

각 구간에 진입할 때 그 시각의 속도를 사용하고, 통과 중 다음 시간대가 되면 남은 거리에 새 속도를 적용한다. 출발 시각의 속도를 모든 구간에 고정하거나, 시간 경계를 넘은 긴 구간을 한 번에 나누지 않고 계산하지 않는다.

계산 예: 08:59:30에 1,000m 구간 진입, 08시는 36km/h·09시는 72km/h라면 첫 30초에 300m, 남은 700m에 35초다. 총 65초. 이 방식은 뒤에 출발한 차량이 시간 경계의 수식 때문에 앞선 차량을 추월하는 오류(FIFO 위반)를 막는다. 데이터에 별도의 신호대기 초를 다시 더하지 않는다.

5 전처리를 진행한 순서와 이유

5 1 원본을 고정하고 식별자를 보존했다

먼저 입력 파일을 식별하고 SHA256 해시를 기록했다. 해시는 같은 이름의 파일이 실제로 같은 내용인지 비교하는 지문이다. 원문 태그와 이미 채택한 검토 근거를 따로 보존하고, 새 계산 결과는 별도 DB에 생성한다. 해시 일치는 파일 동일성의 증거이며 원본의 현실 정확도를 인증하지는 않는다.

강남 자료에서는 위상 수정 전후에 같은 edge_id가 다른 도로 형상을 가리키는 문제가 확인됐다. 비교한 12,585개 중 11,955개가 달랐다. 따라서 과거 어린이구역·사고 파일을 현재 도로와 edge_id 숫자만으로 결합하지 않는다. 대응 계보를 확인하고 분할 구간은 다시 공간 계산해야 한다. [I06]

5 2 좌표와 도로 길이를 맞췄다

화면과 GeoJSON 교환은 EPSG 4326의 경도·위도 순서다. 거리와 반경 계산은 미터 단위인 EPSG 5186으로 통일했다. TAAS와 정밀지도에서 제공한 EPSG 5179 좌표는 필요한 경우 5186으로 변환했다. 좌표계 이름을 붙이는 작업과 실제 좌표를 변환하는 작업은 다르다.

도로 geometry는 유효한 양의 길이 LineString인지 확인하고, 도형 길이와 length_m이 일치하는지 검사했다. 현 입력은 두 점으로 이루어진 edge들이다. OSM의 원래 node 연결 순서와 좌표를 대조하여 제공 PBF 기준 연결을 유지했는지 확인했다. 다리와 평면 도로가 지도에서 교차해 보인다는 이유만으로 연결 node를 새로 만들지 않는다.

예시 GeoJSON의 [127.0331208, 37.5110356]은 경도·위도다. 두 숫자를 뒤집으면 다른 위치가 된다. 100m 원을 만들 때 위경도 숫자에 100을 더하는 방식은 사용할 수 없다. 먼저 미터 좌표계에서 반경과 길이를 계산한다.

5 3 물리 도로를 진행 방향으로 나눴다

edge의 원래 방향을 유지하고, 정방향 arc ID는 2 × edge_id, 역방향은 2 × edge_id + 1로 정했다. 양방향 도로는 두 arc를 만들고, 일방통행은 허용 방향만 만든다. 정방향과 역방향은 북쪽·남쪽이 아니라 OSM 선의 좌표 순서를 기준으로 한다. OSM의 forward/backward 태그도 같은 원리다. [E01, E02]

예시 edge_id 100의 원래 선이 node 10에서 20으로 이어지면 arc 200은 10→20, arc 201은 20→10이다. 길이는 같아도 차로 수·속도·접근 조건은 방향에 따라 다를 수 있다. 두 방향을 하나의 road_link_id로 뭉개면 역주행과 방향 속성 오류를 검출하기 어렵다.

5 4 통행 조건과 회전 제한을 적용했다

일반 승용차를 대상으로 도로 및 node의 접근 태그를 해석했다. 접근 허용 여부가 불명확하거나 시간·차량 크기 조건을 평가할 수 없는 구간은 정적 탐색에서 보류했다. 알려진 금지 회전과 지정 방향 회전은 arc 전이 또는 여러 arc 시퀀스로 저장했다.

길이 연결되어 있다는 사실만으로 모든 회전이 허용되지는 않는다. 또한 직전 두 arc만 검사하면 여러 도로를 거친 후 발생하는 via-way 제한을 놓칠 수 있으므로, 지나온 제한 이력을 탐색 상태에 포함한다. 상세 조건은 다음 장에 정리했다. [I07, E03]

5 5 원문 속성에서 해석값과 추정값을 분리했다

차로·폭·속도는 먼저 원문을 파싱했다. 유효한 원문이 없으면 검토된 보완값이나 고정한 도로 기능 규칙을 사용하되, 원문을 덮어쓰지 않고 basis와 추정 여부를 함께 저장했다. 해석이 모순되거나 지원하지 않는 값은 NULL 또는 보류 사유로 남겼다.

5 6 시설과 사고를 공간적으로 연결했다

시설은 포인트에서 100m 이내에 닿는 edge를 찾았다. 추가로 원 내부 구간의 합집합을 계산했다. 사고는 포인트 자체를 보존하고, edge에서 50m 이내의 알려진 사고 수를 참고값으로 계산했다. 두 공간 연산 모두 가까움을 나타내며 법정 구역 경계나 사고의 확정 도로 귀속을 만들어내지는 않는다.

5 7 경로 계산과 전달 계약을 고정했다

edge·arc·전이 속성을 실제 통과 순서와 비율에 따라 집계하는 공통 계산기를 만들었다. 이후 동일 경로 48건의 거리·raw6·내부시간이 직전 개발본과 일치하는지 확인하고, 다른 데이터 버전·feature 순서·노출 기록·scale 값의 혼용을 거절하도록 계약 검사를 보강했다.

7 차로와 폭과 속도의 세부 규칙

7 1 차로 수는 어느 방향의 값인지 먼저 판단한다

OSM lanes는 해당 way가 나타내는 차도의 총 차로 수다. 양방향 하나의 way이면 양방향 합이고, 분리된 일방향 차도이면 해당 차도 값이다. lanes:forward와 lanes:backward는 원래 way 방향 기준이다. 양방향 총 4차로를 근거 없이 방향별 2차로로 나누거나 일방향 2차로를 왕복 4차로로 늘리지 않는다. [E01]

총 차로 분류에서는 정수 표현을 요구하고, 총합이 없지만 양 방향 값이 모두 유효하면 합산한다. 방향 차로와 공용 차로의 합이 총 차로를 초과하거나 conditional 표현이 있으면 모순·조건부 상태를 남긴다. 최종 총 차로는 L1, L2_3, L4_5, L6_PLUS, UNKNOWN으로도 구분한다.

합류 feature의 방향 차로 해석은 더 엄격하다. 명시된 해당 방향 차로를 우선하고, 일방향이면 총 차로를 사용할 수 있다. 양방향 총 차로가 2 이하이면 ‘해당 방향 3차로 이상은 아님’까지 판단할 수 있지만 정확한 방향별 차로 수는 만들지 않는다. 총 차로가 더 크고 방향값이 없으면 방향 차로는 미상이다. 방향 파서는 명시된 0도 유효한 양의 차로로 받지 않으므로 총 차로 파서와 품질 결과가 다를 수 있다. [I08]

7 3 폴리곤 폭은 제한적으로 채택했다

도로명주소 폭 후보는 위치와 의미가 다를 수 있어 원문의 ROAD_BT 값을 곧바로 주행 도로폭으로 쓰지 않았다. 별도 검토에서는 도로 25%·50%·75% 위치에서 도로에 수직인 단면을 구하고 세 결과가 안정적인 경우만 폴리곤 폭 추정으로 채택했다. [I09]

채택 조건은 유일한 주소 후보, 단일 도로 폴리곤 내부, bridge·tunnel·비영 layer 보류 없음, 정적 통행 보류 없음, 교차 node에서 20m 초과, 방향 변화 10도 이하, 단면이 유일하고 100m 측정선 끝에 잘리지 않음이다. 세 표본이 모두 유효하고 동일 폴리곤에 속하며 (최댓값−최솟값)/중앙값 ≤ 0.2일 때 중앙값을 쓴다.

결과적으로 14개 edge만 채택했다. 이 조건 역시 외부 폭을 잘못 붙이는 일을 줄이기 위한 개발 검사 조건이다. 보도·주차 공간을 포함할 수 있는 도로 폴리곤 단면을 실측 차도 유효폭이라고 표현하지 않는다. 원래 폴리곤 취득과 후보 선정 전 과정은 review2 재생성 범위 밖이며 채택 근거를 고정 입력으로 제공한다.

7 5 속도 원문과 내부시간의 구분

해당 방향 maxspeed:forward 또는 maxspeed:backward가 있으면 일반 maxspeed보다 우선한다. 숫자·km/h를 파싱하고 mph는 1.609344를 곱해 환산하되 별도 검토 대상으로 둔다. 0 이하, 지원하지 않는 복합표현, 조건부 속도는 보류한다. 5km/h 미만 또는 130km/h 초과도 프로젝트 이상값 검사에서 review로 표시한다. 이 범위는 법정 속도 범위를 정의한 것이 아니다. [I08, E05]

시간대 프로필을 적용할 수 없는 부분의 fallback 계산 속도는 적용 가능한 OSM 파싱속도 × 0.7, 교차 출처 보완속도 × 0.7, 도로 기능 기본속도 순서다. 0.7은 현재 실측으로 적합한 보정계수가 아니다. 기본속도에는 0.7을 한 번 더 곱하지 않는다.

8 1 시설 포인트 반경 100m

현행은 시설 포인트에서 직선거리 100m 이하인 도로를 근접 도로로 분류한다. 포인트와 선의 최단거리를 계산하므로 edge의 중점만 비교하지 않는다. 1,626개 시설에서 전 도로를 재계산했을 때 385,020 edge의 기존 100m 시설 개수와 모두 일치했다. [I04]

동일 위치의 시설은 원본 기록별로 보존한다. facility_count에는 원본 중복 기록이 포함될 수 있지만, 근접 여부와 원 내부 합집합 길이에는 중복 가산하지 않는다. 화면의 100m 원은 표시용 다각형 근사이고, 내부 길이는 실제 원과 선의 교차 비율로 계산한다.

8 2 사고 데이터는 참고 오버레이로 보존한다

TAAS 2025년 서울 자료는 34,309개 고유 사고 ID와 좌표를 갖는다. CSV와 GPKG의 ID 집합과 좌표 변환을 대조했다. edge_feature의 accident_known_count_50m는 도로선에서 50m 이내에 있는 제공 사고 포인트 수다. 해당 edge에서 발생한 사고 수로 확정하지 않는다. [I10]

같은 사고가 가까운 여러 edge의 50m 범위에 들어갈 수 있다. 따라서 한 경로의 edge별 사고 수를 단순 합하면 중복될 수 있다. 경로의 고유 근접 사고 수가 필요하면 사고 ID 집합을 합쳐 중복을 제거하는 별도 집계 규칙을 정의한다. 현행 raw6와 X8에는 이 사고 수를 넣지 않는다.

서울 경계에서 50m 안쪽으로 줄인 영역이 전체 edge를 포함하는 경우 within_seoul_50m_geometry로 표시한다. 그렇지 않으면 boundary_incomplete다. 경계 밖 사고가 제공되지 않았을 가능성을 남기는 장치다. 사고 0인 도로를 ‘안전’으로 라벨링하지 않는다.

9 2 교차로와 회전은 전이에서 센다

물리 node 차수는 자동차 도로로 분류된 물리 연결에서 고유 이웃 node 수를 센 값이다. 왕복 arc를 둘로 늘렸다고 차수가 두 배가 되지 않는다. 차수가 5 이상인 전이를 통과할 때 COMPLEX_INTERSECTION에 1을 더한다. 경로의 출발점에 있다는 이유만으로 교차로를 가산하지 않는다.

UNFAMILIAR_TURN은 node 차수가 3 이상이거나 OSM way가 바뀌는 전이 중 절대 회전각이 100도 이상인 경우 1을 더한다. 회전각은 진입·진출 방향 벡터의 각도다. 같은 방향 직진은 0도, 직각 회전은 약 90도다. 90도 좌회전도 신호나 비보호 여부에 따라 힘들 수 있지만 현행 100도 feature에서는 0일 수 있다. 따라서 이 feature를 전체 좌회전 수 또는 법적 유턴 수로 표시하지 않는다.

9 3 연속 조작은 앞선 조작을 기억해야 한다

조작 후보는 ‘node 차수 3 이상 또는 way 변경’이면서 ‘절대각 45도 이상 또는 _link 진입·이탈’인 전이다. 경로의 누적거리에서 조작 위치를 기록하고, 바로 이웃한 조작 간 거리가 0 초과 100m 이하이면 1개를 센다.

예시 조작 위치가 누적거리 100m, 180m, 350m, 430m이면 간격은 80m, 170m, 80m다. CONSECUTIVE_ACTION은 2다. 네 조작이 있으므로 4가 되는 것도, 서로 가능한 모든 조작쌍을 조합하는 것도 아니다. 긴 간격 뒤에 새로 가까운 두 조작이 생기면 다시 가산한다.

이 값은 경로 이력에 의존한다. arc마다 고정 점수를 하나 붙여 더하는 것만으로는 계산할 수 없다. A* 탐색 비용에 포함하려면 직전 조작 이후 이동거리 같은 상태가 추가로 필요하다. 현 서비스는 이 요소를 최종 후보 평가에 집계한다. 모든 개인화 비용의 전역 최적화를 제공하지 않는다.

9 4 부분구간과 반복통과

각 segment는 arc_id와 start_fraction·end_fraction을 가진다. 비율은 진행 방향 기준으로 0 ≤ start < end ≤ 1이며 부분구간은 첫 segment와 마지막 segment에만 허용한다. 중간 arc는 온전히 지나야 연결 node가 맞는다.

예시 200m arc를 0.25부터 0.75까지 지나면 100m를 집계한다. narrow_score가 0.5라면 좁음 기여는 50 score·m다. 역방향 arc의 이 구간을 원래 edge 기준으로 바꾸면 [1−0.75, 1−0.25], 즉 [0.25, 0.75]다. 비대칭 구간 [0.1, 0.4]는 원래 edge의 [0.6, 0.9]에 대응한다.

같은 도로를 나중에 다시 통과하면 실제 반복 노출을 다시 더한다. 방문 edge_id를 중복 제거하면 경로의 거리와 부담이 줄어드는 오류가 생긴다. 다만 같은 edge로 즉시 되돌아가는 동작은 현재 참조 전이 정책에서 별도 제외되어 있다.

상태에는 node뿐 아니라 직전 arc와 제한 시퀀스 이력이 들어간다. 단순 node-only 탐색으로 via-way 제한을 무시하면 안 된다. 최소시간 탐색은 시간에 따라 달라지는 구간 비용을 사용한다. 직선거리의 하한과 최대속도 130km/h로 휴리스틱을 구성했다. 제한된 표본에서 휴리스틱 0의 Dijkstra와 일치했다.

후보는 시간·거리·설문 부담·좁은 도로 회피의 네 가지 탐색으로 만들고 중복을 제거한다. 최종 raw6 여섯 개를 모두 다시 계산하고 같은 출발시각의 최소시간 + Q3×60초 이내만 남긴다. 선호 경로는 이 후보 중 설문 가중 점수가 가장 낮은 경로다. 거리우선도 Q3를 통과한 생성 후보 중 최단거리다. 모든 경로 공간에서 여섯 요소와 Q3를 동시에 전역 최적화했다는 주장은 하지 않는다. CONSECUTIVE_ACTION은 생성 비용에 직접 넣지 않고 최종 후보 평가에 정확히 집계한다.

현 후보 정렬의 고정 진단 scale은 [10,1000,1000,10,10,1000], burden_score는 Σ(weight × raw/scale)이다. 이것은 학습용 train-only X8 scaler가 아니다. 탐색에서 일부 비음수 비용을 사용해 다양한 후보를 확보하고 최종 전체 raw6로 순위를 매기는 역할을 구분한다. 모든 선호가 0이면 시간 동률 기준으로 선택되어도 정상이다.

Q3 예: 같은 시간 모델로 최소시간 300초, Q3=5분이면 제한은 600초다. 선호 점수가 더 좋아도 620초 후보는 제외한다. 화면에 반올림된 5분을 내부 최소시간으로 역산하지 않는다. 외부 카카오 표시시간을 이 최소값에 섞지 않는다.

시간은 현재 화면의 정수 분 × 60초를 저장한다. 숨겨진 정밀 내부초를 실제로 표시한 것처럼 학습하지 않는다. internal_duration_s는 탐색·Q3·진단에 별도로 보존한다. Y는 실제 사람이 A를 택하면 1, B를 택하면 0이다. 위험이 낮다고 코드가 추정한 후보를 정답으로 만들지 않는다. 후보 ID 정렬로 A/B를 고정하고 X(A,B)=−X(B,A)인지 확인한다.

예를 들어 A의 표시시간 240초·거리 1,400m, B가 300초·1,600m이고 시간 scale=60·거리 scale=1,000이면 X 첫 두 칸은 [-1,-0.2]다. 좁음 값 A=200·B=400, 좁음 가중치 0.5·scale=1,000이면 해당 칸은 -0.1이다. 이 숫자는 설명 예이며 학습 정답을 임의로 생성한 것이 아니다.

실제 후보가 두 개 이상 노출된 선택만 pair 학습에 사용한다. 선택 1개에서 다른 후보들과 여러 pair가 나오면 sample_weight=1/(노출후보 수−1)로 한 선택이 지나치게 중복되지 않게 한다. 단순 카드 미리보기, 미노출 후보, 선택을 취소한 검색은 정답으로 쓰지 않는다.

export_choices.py --output 새파일.jsonl은 DB의 실제 선택과 immutable snapshot을 모아 내보낸다. 사용자를 해시로 60/20/20 분할하므로 같은 사용자 기록이 train과 test에 섞이지 않는다. 사용자 수가 적으면 한 split이 비어 있을 수 있으므로 실제 학습 수량·분할 가능성은 ML 담당자가 확인한다. scale은 train만으로 적합하고 scale_version·fit_manifest_sha256·scaler_sha256을 별도 학습 view에 붙인 후 tools/api.py의 make_training_pairs를 사용한다. 저장된 서비스 snapshot을 나중에 바꾸지 않는다.

5개 버전·사용자·검색·노출·프로필·모델·출발시각·feature 순서·scale이 서로 다르면 X8을 만들지 않는다. 현재 함수는 INTERNAL_HOURLY 표시시간을 허용한다. 과거 정적 ETA의 snapshot을 버전 이름만 바꿔 학습에 섞지 않는다. 현재 앱은 survey_only_v1이며 학습 완료 LR/XGBoost 모델이나 이력으로 보정된 effective_weights가 들어 있다고 해석하면 안 된다.

이전에 같은 OD10을 조회한 네이버·카카오 거리우선은 약 1.9km, 내부 거리 경로는 1.422km였다. 두 내비는 언주로→테헤란로, 내부는 논현로·이면도로를 이용하는 차이가 있었다. 출발 방향이나 의심 회전 하나를 바꿔도 차이가 완전히 해소되지 않았다. 비교 결과의 요약과 현재 한계는 evidence/final_child100_review.json 및 이 README 16장에 남겼다.

16.2 팀 구현을 건드리지 않고 다원이 할 수 있는 일

지금은 동결 DB를 읽기 전용으로 두고 근거와 수정 후보를 별도 파일에 모으는 작업을 하면 된다. 이 단계는 A*·모델의 입력값·컬럼·ID에 영향을 주지 않는다. 실제 적용까지 완전히 영향이 없다는 뜻은 아니다. 도로 제약·속도·시설 위치·좁음 값을 바꾸면 경로 또는 feature가 달라지므로 새 배포와 재계산이 필요하다.

아래 우선순위는 현 데이터의 미확인 지점과 서비스 시연 범위를 기준으로 한 작업 제안이다. 완료된 정확도 개선 결과가 아니다. 남은 5일에는 P0 한두 대표 경로를 우선 확인하고, 나머지는 증거 수집까지만 하여 팀 구현을 멈추지 않는다.

P1의 ‘독립 판독’은 53,516개 채택 규칙을 같은 코드로 다시 검사하는 것과 다르다. 사람이 실제 형상·방향과 근거를 판독해 정답/오답/판단불가를 기록하고, 가능하면 매칭 규칙을 조정할 때 보지 않은 표본을 평가용으로 둔다. 현재 전달본은 전수 채택 규칙과 계산 일관성 검증을 완료했으며 이런 독립 정답표로 매칭 정확도를 인증한 상태는 아니다.

현재 매칭 거리 비율 10.946%는 지원 arc를 방향별로 센 값이다. TOPIS는 모든 골목을 덮는 관측망이 아니므로 미매칭 도로를 억지로 전부 연결하는 작업은 우선하지 않는다. 공식 속도정보는 도로별 관측과 가공 방식을 설명하고 있으며, 서비스링크와 표준링크의 연결은 공식 매핑정보로 보강할 수 있다. 기존 임계값을 완화해 매칭 건수만 늘리는 방식은 이 동결본에 적용하지 않는다. TOPIS 속도정보, 서울시 교통소통 표준링크 매핑정보.

회전 검토는 from·via·to와 no/only 순서를 함께 확인한다. 단일 노드에서 좌회전 표시만 확인해서 via-way 제한을 대체하지 않는다. 이 표현의 기준은 OSM restriction 설명에 있다. 그 설명 자체가 특정 서울 교차로의 현재 통행 허용 근거가 되지는 않는다.

근거 기록 예: review_id=OD10_TURN_01, base_release=현재 v3, arc_ids=실제 해당 방향 ID 목록, issue=첫 갈림 지점의 좌회전 허용 여부, observed_at=확인 시각, source_url=지도/공식 자료 주소, before_value=현재 허용, proposed_value=미정, confidence=판단불가, status=EVIDENCE_ONLY. 통행 가능/불가가 확인되기 전에는 DB의 허용값을 바꾸지 않는다. 좌표·지도 캡처·요청 조건을 함께 남겨 팀원이 재확인할 수 있게 한다.

새 후보 파일은 final DB 밖에 두고 release_id·edge_id/arc_id·근거 시각·원값·제안값·사유를 기록한다. DB의 기존 행 수정, ID 재부여, 100m 반경 재변경, feature 순서 변경, 관측 시간 월 교체를 현재 버전에서 수행하지 않는다. 명백한 통행 오류가 확인되면 영향 경로와 회귀 결과를 묶어 새 버전을 한 번에 인수한다.

부록 A 정제 파일의 실제 컬럼 사전

실제 DB 스키마에서 확인한 컬럼명과 자료형이다. INTEGER·REAL·TEXT·BLOB은 SQLite 저장형이며, 서비스 이전 시 정수 ID는 BIGINT, 계산 수치는 double precision, JSON 문자열은 검증 후 JSONB, 공간형은 CRS를 가진 PostGIS geometry로 매핑할 수 있다. 이 매핑은 저장 설계이며 실제 migration 실행 결과가 아니다.

핵심 적재 출발점은 road_attributes_v1과 arc_attributes_v1 view다. edge_policy와 arc_policy는 그 기반 테이블이므로 값이 중복된다. 기초 features.sqlite의 narrow_score는 현행 전체 385,020행에서 NULL로 남아 있으며 최종 점수는 feature_policy.sqlite에서 읽는다. 이름만 보고 잘못된 테이블을 선택하지 않는다.

정적 시간 컬럼 eta_dev_seconds·eta_dev_kph는 시간대 미적용 시의 기본값이다. 최종 서비스의 시간은 hourly.py가 반환한 internal_duration_s다. 정적 DB에는 이전 raw6의 버전 메타데이터를 보존하므로 이 DB의 과거 eta_version을 서비스 응답 버전과 혼동하지 않는다.

이 팀 전달본은 검증된 정제 데이터를 사용하는 실행용 패키지다. 원본부터 전체 재생성하는 도구와 대용량 입력은 포함하지 않는다. 현재 시간대 계산과 보호구역 계산은 동봉된 검증 도구로 다시 확인할 수 있다. 기관 원자료부터 재생성이 필요하면 데이터 담당자가 보관한 전체본을 사용한다.

DB 연결 검사를 재실행하려면 service/tests/final에서 npm ci를 한 뒤, 루트에서 가상환경 Python으로 tools/test_service_connection.py를 실행한다. worker와 Node를 함께 시작하여 실제 HTTP로 계산하고 별도의 PostgreSQL 엔진에 시험 행을 넣는다. 시험 사용자·선택은 모두 가상 계정이며 학습용 실제 라벨이 아니다. 결과는 local_test_results에 저장하고 배포 기준의 evidence를 덮어쓰지 않는다.

과거 고정 근거의 파일 인덱스 이 전달본 안에서 근거 찾기

설명과 사용에 필요한 현재 근거는 모두 이 패키지 안에 있다. source_register.json은 원본 출처와 적용 정책, evidence/final_child100_review.json은 최종 비교 판정, evidence/child100_validation.json은 100m 공간 검산, evidence/hourly_build_summary.json과 hourly_validation.json은 시간대 연결·검증, tools/runtime/current_feature_contract.json은 현 feature 계약이다. 초기 기획서·과거 단계 문서·원기관 파일은 실행 기준이 아니므로 제외했다.

도로 태그·기준을 확인한 외부 근거 외부 원문과 사용한 범위

E01 OpenStreetMap lanes 설명. 차로 수의 way 기준과 forward·backward 의미를 확인했다. 우리 좁음·합류 점수의 실증 타당성을 보증하는 자료는 아니다.

E02 OpenStreetMap oneway 설명. 일방통행과 원래 선 방향의 관계를 확인했다. 제공 OSM의 현장 완전성은 별도다.

E03 OpenStreetMap restriction 관계 설명. from·via·to와 no·only 제한 구조의 의미를 확인했다. 기록되지 않은 제한을 복원했다는 뜻은 아니다.

E04 OpenStreetMap width 설명. 원문 폭의 의미를 구분하는 참고다. 우리 3.5m·5.5m 부담 임계값이나 폴리곤 유효폭을 인증하지 않는다.

E05 OpenStreetMap maxspeed 설명. 속도 제한 태그와 단위·방향 정보 해석의 참고다. 0.7 보정계수와 도로 기능 기본속도는 별도의 개발 가정이다.

E06 서울 TOPIS 속도 정보. 관측 속도 자료의 제공 범위와 수집 설명을 참고했다. 2026년 8월 실험 결과는 제공 Excel을 분석한 내부 근거 I12에서 나온다.

E07 카카오모빌리티 자동차 길찾기 API. 출발 진행각, RECOMMEND·TIME·DISTANCE, 회피 옵션과 상세 경로 응답을 기록하는 비교 방법의 근거다. 현재 웹 비교 기록에 API 상세 좌표가 모두 확보됐다는 의미는 아니다.

E08 Campigotto 외 FAVOUR 논문. 초기 선호와 사용 중 선택을 활용한 프로필 갱신을 참고했다. 우리 서비스는 자동차 운전부담을 다루는 별도 설계이며 논문의 모든 모델과 실험을 재현한 것은 아니다.

E09 서울시 교통 링크 매핑정보. 서비스링크와 표준링크 사이의 대응 자료를 확인하는 출처다. OSM arc까지 바로 연결되는 완성 대응표로 취급하지 않는다.

정밀도로지도 취득 경로는 국토정보플랫폼 정밀도로지도다. 이번 문서의 객체 수·날짜·인코딩·매칭 후보는 제공 SEC003·004·005 원본과 I11에 근거한다. 사이트의 현재 다운로드 목록을 다시 확인한 결과로 표현하지 않는다.

일반 계산은 동봉 data와 tools를 함께 사용한다. 현재 설명의 유일한 시작 문서는 README.html이다.
